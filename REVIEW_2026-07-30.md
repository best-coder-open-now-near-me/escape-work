## Questions for the designer

Four findings below are questions about intent wearing a bug's clothes. Each
carries options, the cost of each, and a recommendation.

**1. In a fight, should the camera follow the member you are STEERING, or the
leader?** (Finding 1 — the branch's own feature.) Today the rig always follows
the leader's body, and `Home` on a steered teammate silently detaches the camera
instead of centring it.
- **A (recommended)** — follow the steered combatant. `focusCameraOn` compares
  against the acting body, and the update loop follows it too. The view belongs
  with whoever you drive, which is what `ARCHITECTURE.md` already claims.
  Cost: `controls.follow`'s target becomes `combat.actingActor` in combat, and
  main.js must repaint the follow target on every steer.
- **B** — keep leader-follow, but make a recenter aimed at a non-leader keep
  re-gliding as they walk. Cheaper; leaves the camera behind the wrong body
  whenever you are not looking.
- **C** — declare leader-follow correct and change the key's promise instead.
  Cheapest; `Home` becomes "go to the leader", which is not what BG3 does.

**2. Should the two HR buffs and the Mail Room swap work out of combat?**
(Finding 5.) `main.js` has a whole dispatch path for an armed friendly verb
clicked on a teammate out of combat — and the arming gate refuses to arm any of
them, with a message that names the wrong reason.
- **A (recommended)** — yes. Add `buff` and ally-aimed `mobility` to
  `combatOnlyReason`'s pass list. This is the precedent already set for `purge`
  ("at its MOST useful out here") and Take Cover, and it makes two of six
  classes' identity verbs reachable outside a fight.
- **B** — no; keep them combat-only, and fix the refusal message to say so
  honestly. Then delete the unreachable dispatch path at `main.js:1279`.

**3. Should a staple hit look like shredded paper?** (Finding 6.) Every ranged
hit in the game lands with the paper impact, and the projectile's flight is
chosen by an `id ===` test in `combat.js`.
- **A (recommended)** — `projectile` and `impact` become fields on the action
  entry. Costs one data edit per ranged action; removes the last id-special-case
  from the strike path and satisfies "content is data, code is systems".
- **B** — leave it. Two visual details, and nobody has complained.

**4. Retro-tag the nine untagged plan docs, or accept them as `[proposed]`?**
(Finding 12.) `POWERS_PLAN.md` is the live case: written the day the tagging rule
landed, edited two days later, still untagged — and its decisions are shipped as
the six-class kit.
- **A (recommended)** — retro-tag `POWERS_PLAN.md` only, now, since it is the one
  whose decisions are both post-rule and already in the game.
  `TACTICS_PLAN.md` sets the precedent for retro-tagging a pre-existing doc.
- **B** — retro-tag all nine. Thorough, and a large pass over docs nobody is
  currently building against.
- **C** — leave them; CLAUDE.md's default already makes them `[proposed]`.
  Cheapest, and it means every citation of them is a citation of a guess.

## Findings

Severity is about consequence to a player or to the next person editing the file.

### 1. `Home` detaches the camera from the member you are steering — high

`src/main.js:2987` (`focusCameraOn`), `src/main.js:3409` (the follow call),
`src/combat.js:1624` (`makeActive`).

The rig's follow target is `player` — the *leader's* actor — every frame:

```js
const pp = player.entity ? player.entity.getPosition() : player;
controls.follow({ x: pp.x, z: pp.z }, dt);
```

`combat.steerMember` → `makeActive` deliberately does not re-key `player`
(`ARCHITECTURE.md`: steering uses "never `switchLeader`, which re-keys the
out-of-combat world"). `player` is assigned in exactly five places
(`main.js:144, 720, 738, 1742, 3466`) and none of them runs on a steer.

So whenever the steered member is not the leader, `combat.actingActor !== player`,
and `focusCameraOn` takes its else-branch:

```js
if (actor === player) { controls.recenter(); return; }
const p = actor.entity?.getPosition();
if (p) controls.panTo({ x: p.x, z: p.z });
```

`panTo` sets `free = true`. The consequences, all in a multi-member fight:

- **`Home` — the key whose comment reads "put the camera back on whoever you're
  driving" — detaches the rig** and freezes it at that member's position at that
  instant. It does not follow them as they walk.
- The bottom-left profile card's double-click (`main.js:3007`) does the same, and
  the card is showing that member (`paintHud` follows initiative).
- Double-clicking that member's own party-bar card or initiative row: same.
- Nothing re-attaches until a control change (leader switch, survivor steps up,
  fight starts), so the view stays frozen for the rest of the fight.
- Independently: for the whole fight the camera follows the leader, not the
  member being driven.

Traced, not reproduced. `tests/e2e/camera.spec.js` fights with a **one-member
party**, so `actingActor === player` always holds and this branch is never
exercised — the spec's combat case asserts the true-negative and passes.

Fix depends on Question 1. Under (A): `controls.follow` takes the acting body in
combat, and `focusCameraOn` compares against that same body.

### 2. Player-typed names go into `innerHTML` unescaped — medium

`src/combat.js:715` and `:1746`; `src/creation.js:76`; `src/ui/screens.js:30`.

```js
const slotName = (s) => (s.member ? s.member.sheet.name : s.unit.def.name);
...
+ `<span>${slotName(s)} &middot; ${dead ? '—' : hp}`
```

into `strip.innerHTML`. The name is player input from character creation, and
`cleanName` only collapses whitespace, trims, and slices:

```js
const cleaned = String(raw ?? '').replace(/\s+/g, ' ').trim().slice(0, NAME_MAX);
```

`NAME_MAX` is 24 — enough for `<svg onload=…>`, and a bare `<b>` is enough to
corrupt the initiative strip's layout. An `esc()` helper exists in exactly one
file, `ui/screens.js`; every other surface interpolates raw.

This is local single-player, so the injection is self-inflicted and the security
consequence is small. The correctness consequence is not: a name with `<` in it
breaks the HUD. Fix: lift `esc` into `ui/chrome.js` (the shared-palette module
every surface already imports) and route every name, item label and flavor string
through it.

### 3. The pan keys `preventDefault()` before any gate — medium-low

`src/main.js:3026` and `:3395`.

```js
if (PAN_CODES[e.code] && !e.ctrlKey && !e.metaKey) {
  panHeld.add(PAN_CODES[e.code]);
  e.preventDefault();
}
```

This runs on every `keydown`, before any check of what is focused or open. Two
consequences:

- Arrow keys stop scrolling **any** scrollable DOM panel — pockets, the shop
  list, the character sheet — because the default is suppressed unconditionally.
  The comment justifies the `preventDefault` by the itch.io iframe scrolling the
  host page, which is a real problem, but the fix is aimed at the whole document.
- `modalOpen()` (`main.js:1348`) is only `dialogue.visible || shopping.visible`.
  The update loop's pan gate uses it, so WASD still pans the world behind the
  level-up screen, the character sheet, the pockets panel and the game menu.

The typed-name field is safe (`ui/creation.js:140` stops propagation) and so is
the god panel (`god.js:121`), so this is not a text-entry bug today — it is a
bug for every scrollable surface, and it will become a text-entry bug the first
time an input is added without the `stopPropagation` incantation.

Fix: gate the `preventDefault` on the same condition the pan itself uses, and
widen `modalOpen()` (or introduce a `uiCapturesKeys()` that the panels register
with) so it means "a panel owns the keyboard" rather than "dialogue or shop".

3. **`src/combat-ai.js`** (`aiAdvance`, `standTilePath`, `engageMemo`,

### 5. Three powers are dispatchable out of combat but cannot be armed there — medium

`src/main.js:1447` (`combatOnlyReason`), its whitelist at `:1456`, vs `src/main.js:1279` and
`src/powers.js:191` (`aimsAtAlly`).

`combatOnlyReason` whitelists by hand:

```js
if (!a || t === 'attack' || t === 'shove' || t === 'summon' || t === 'purge' || t === 'cover') return null;
if (t === 'heal') return `${a.label} is for a fight - out here, heal from your pockets.`;
return `${a.label} only means something once someone is swinging at you.`;
```

`aimsAtAlly` is `isFriendly(a) || aimsAtAnyone(a) || (isMobility(a) &&
ALLY_MODES.has(a.mode))` — so it is true for `type: 'buff'` and for an
ally-aimed mobility, neither of which the whitelist passes. Concretely:

| action | type | class | out of combat |
|---|---|---|---|
| `performance-review` | buff | Human Resources | refused |
| `onboarding` | buff | Human Resources | refused |
| `courier-swap` | mobility (ally) | Mail Room | refused |

Two consequences:

- **The refusal names the wrong reason.** "Onboarding only means something once
  someone is swinging at you" is false: it is a buff on a teammate, and the
  message is the one written for `defend`.
- **`main.js:1279` is unreachable for buffs.** The armed-friendly-verb branch on
  a party-member click can only ever be entered by `reboot`, the sole `purge`.
  The comment above it says it exists because "a power aimed at a colleague out
  of combat did nothing" — for the two actual buff powers, it still does nothing,
  because arming them is refused one layer up.

This is the fourth hand-maintained enumeration of action types in the codebase
(`main.js:1260`, `main.js:1456`, `combat.js:3272`, plus the predicate set in
`powers.js`), and the first three disagree with each other about which types
they list. See Question 2 for the fix's shape; either way the whitelist should
be replaced by a predicate in `powers.js` so there is one answer.

### 6. Ranged impact FX are hardcoded, and every ranged hit is paper — medium

`src/combat.js:1833` and `:1870`. `REVIEW.md` predicted this would persist "in a
new shape"; it has.

```js
let flight = 'shot';
if (id === 'paper-airplane') flight = 'plane';
else if (a.ammoCost) flight = 'ball';
...
hitFx(en, rangeOf(id) ? 'paper' : 'melee', active);
```

Firing the staple gun or the spitball straw produces the paper-shred impact,
because the impact is selected by "is this ranged", not by what it is. And the
flight is selected by an id equality test — adding a projectile means editing
`combat.js`, which is the one rule `ARCHITECTURE.md` opens with. See Question 3.

### 7. `ammoCost` still means three things — medium-low

`REVIEW.md` credited `rangeOf()` with fixing the `ammoCost`-as-range confusion. It
fixed one of three uses. `ammoCost` currently means:

- the paper cost of a throw (`ammoCostOf`, `stats.js:541`) — its real meaning;
- **"is this action throwable"** — `combat.js:319`,
  `Object.keys(ACTIONS).filter((id) => ACTIONS[id].ammoCost)`, which is what
  populates every member's throw list;
- **the default range** — `stats.js:527`, `return a.ammoCost ? THROW_RANGE : 0`;
- and at `combat.js:1835`, the projectile's *appearance*.

A ranged action that costs no paper is therefore not throwable and has no default
range. Adding one (a rubber band, a thrown mug) requires giving it a fake
`ammoCost`. Fix: a `throwable: true` flag, or derive from `rangeTiles`/`range`
declared explicitly.

### 9. The `[quick]` CI escape hatch can only fire on direct pushes to main — low

`.github/workflows/ci.yml`. The header documents, at length and correctly, why
`[e2e]` cannot be read from a commit message on a branch: a branch push triggers
nothing, so the only event is `pull_request`, where `github.event.head_commit`
does not exist. It then gives `[e2e]` a PR-title fallback.

`[quick]` has the identical constraint and no fallback:

```yaml
if: ${{ !contains(github.event.head_commit.message, '[quick]') }}
```

On a `pull_request` run this is always true, so the smoke test always runs. The
header presents `[quick]` as the general workflow for visual changes ("Put
`[quick]` in the commit message for a change you will SEE… Deploy still runs, so
a visual tweak is live in about a minute"), and that path only exists for someone
pushing straight to `main`. Fix: add the PR-title form, or say in the header that
`[quick]` is main-only.
